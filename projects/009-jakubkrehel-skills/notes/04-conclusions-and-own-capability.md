# 最终理解与自有网页优化能力

研究收尾：2026-09-06。上游固定版本、来源及许可见[项目 README](../README.md)。

## 我们的判断

这个库提供的是界面知识与执行流程。规则需要模型理解、工具执行和项目上下文配合；加载文档不等于获得确定的优化效果。

本轮从规则示意走到真实页面修复，发现视觉提升有限。RUN-001 修正了文字大小、可见选中提示、搜索标签与空结果恢复，保留整体布局与风格。真实变更和浏览器观察可以证明这些改动发生了，不能证明不用 Skill 就做不到。三种密度候选尚未选定，不作为已完成的设计优化。

因此不主张全量默认加载，也不再为证明其价值而扩大演示。保留源码索引、实验及证据，作为按需参考。未来若反复出现遗漏，再引入能解决该问题的少量规则。

模型越强，通用设计常识可能越不稀缺；项目约束、历史教训和可靠验收更值得沉淀。这是后续实践方向，不宣称已证明所有通用 Skill 失去价值。

## 从参考思路到自己的能力

沉淀对象是“在我们的页面中反复有效的实现与验收经验”。规则应告诉模型在哪个条件下解决什么问题，并要求验证；避免一律换风格、加动画或增大字号。

| 环节 | 对模型的具体约束 | 留存产物 |
| --- | --- | --- |
| 明确任务 | 先说明用户来页面要完成什么、当前障碍是什么 | 一个可操作的用户任务 |
| 观察原页 | 阅读源码、查看真实状态，保留基线；不故意劣化原页 | 原始版本及问题位置 |
| 提出修改 | 每项修改关联问题，说明预期收益与空间、性能或操作代价 | 小范围修改清单 |
| 实施 | 沿用项目组件与规范，保留必要功能；内容来自真实数据 | 可运行的代码差异 |
| 验收 | 复测受影响操作、适用尺寸和状态；没运行的检查明确标注 | 浏览器观察与必要测试 |
| 留存 | 经验证、值得复用的经验才加入规则；偏好单独标记 | 规则、案例与回归场景 |

这份文档是后续使用的约束草案，尚未安装成 Skill，也未建立自动执行平台。

## 可复用的任务约束草案

> 优化指定页面中的一个真实用户流程。先读取项目规范、源码与运行页面，定位影响使用的问题，再实施有依据的修改。保留真实内容与必要行为。每项改动说明问题、位置、预期收益和代价，不以改动数量或视觉差异大小作为成功标准。使用真实组件检查适用的窄屏、内容增长、键盘及空结果场景。修复后提供前后证据和验证结果；无法验证的项目明确说明。没有足够依据时保留原实现。

每次使用时补充页面、用户任务、技术栈、允许范围、设计规范及验收条件。此草案不会覆盖或取代用户当次指令。

## 规则怎样留存

每条经验记录：适用条件、实际问题、实现约束、源码或页面证据、验收步骤、例外和复核日期。规则分三类：

- 必须保留的功能：例如筛选后仍能查看详情，修复不能破坏既有操作。
- 有条件的质量要求：例如空结果导致用户无法继续时，提供适当恢复入口，并实际验证恢复后的列表与焦点。
- 风格偏好：例如卡片密度、圆角和动效，只在项目接受时应用。

不把“正文必须 14px”从本次修复推广为通用规则；也不把对比度改善直接等同于整体体验变好。能用测试可靠验证的要求沉淀为检查，审美取舍保留人工判断。重复、无效或不再适用的规则应合并或删除，避免上下文不断膨胀。

## 以后如何判断是否值得继续

若开展对照实验，固定同一页面快照、模型配置、任务与工具权限，分别使用普通任务指令和追加规则的指令；分别使用隔离上下文，保存输入与输出。最好重复多轮并随机隐藏方案来源后评价。

比较真实问题解决情况、误报、功能回归、用户任务完成情况以及执行成本；视觉评价单独记录，不用字号或修改行数代替收益。只有持续减少遗漏、返工或验收成本，才考虑正式集成。

当前收尾决定：研究资料与实验保留，方法可参考；后续优先沉淀我们自己的网页问题、约束与验证案例。没有宣称已形成经过评测的自有优化系统。
