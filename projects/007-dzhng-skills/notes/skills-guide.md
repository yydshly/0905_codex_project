# 22 项 Skill 能力、使用场景与顺序

研究版本：3631529b7305eec8dd08b3a827f4d8c16342a29a。本文与网页共用 web/data.js 和 web/details.js；修改后运行 node projects/007-dzhng-skills/web/generate-research.mjs。

这是覆盖需求到交付的工程操作规程集合。实际模型、文件、浏览器与持续执行能力由宿主提供；全部技能不必在每个任务里调用。案例为本仓库推演，非上游实测。

![全部 22 项能力与使用顺序示意](../assets/workflow-map.svg)

## 如何读图

主流程是 explore-unknowns → write-spec → implement-spec → review → audit-choices；未完成则继续，全部验收后 close-spec。review 内部顺序是 refactor-clean → code-review → write-docs。实现中穿插行为与视觉验证；模型 CLI、领域技能按需使用。eli5 贯穿解释，write-skills 与 eval-skills 构成独立改进循环。

大功能需要完整规格，小修复可以直接 write-tests 与 review；只有视觉工作才需要相应视觉检查。图的分组和箭头为源码关系的研究归纳，不是程序调度图。

## 工程流程

### explore-unknowns · 把未知变成可讨论的问题

通过四象限探索，厘清事实、待解问题、隐含偏好与潜在风险。

- **具体能力：** 梳理已确认事实、待解问题、隐含偏好与未知风险；用原型、选项和决策表获取具体反馈。
- **使用场景：** 模糊需求、陌生代码库或参考实现研究
- **输入与案例：** 英语阅读器先明确双语呈现、离线需求、同步方式和文档格式。
- **产出：** 带理由的决策与未知地图
- **调用顺序：** 需求模糊时先用，结果交给 write-spec；实现偏离时可返回。
- **限制：** 需要真实材料与用户反馈；探索结束不代表实现完成。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/explore-unknowns/SKILL.md)

### write-spec · 把目标拆成可验收的小块

沿接口边界拆分功能，为每块指定契约、证据与依赖。

- **具体能力：** 沿接口拆分任务，明确输入输出、依赖、可自主决定的范围与验收证据；复杂任务比较独立方案后综合。
- **使用场景：** 多步骤功能、复杂迁移与高风险改动
- **输入与案例：** 将阅读器拆为解析、段落对应、进度恢复，每块都有固定样本验证。
- **产出：** 规格目录、任务依赖与接手说明
- **调用顺序：** 探索后、实现前；出现未知或任务过大时重新拆分。
- **限制：** 规格需要随实现更新；写入验收规则不等于已执行。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/write-spec/SKILL.md)

### implement-spec · 按证据持续推进实现

逐块实现、验证、审查并更新交接状态；独立任务可并行。

- **具体能力：** 读取接手点，逐块实现、验证、审查和记录决策，更新计划继续推进；独立任务并行，有依赖的任务顺序整合。
- **使用场景：** 已有规格的长任务
- **输入与案例：** 先验证文章解析，再实现双语界面，每轮保存证据与下一步状态。
- **产出：** 代码、检查证据与最新任务状态
- **调用顺序：** 主执行循环；每轮 review 与 audit-choices，全部完成再 close-spec。
- **限制：** 需要宿主执行工具与持续运行能力，Markdown 本身不调度进程。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/implement-spec/SKILL.md)

### implement-spec-with-codex · 分开实现与统筹职责

由 Codex 编写代码，主 Agent 负责协调、整合与审查。

- **具体能力：** 沿用 implement-spec；Codex 负责实现，主 Agent 负责任务选择、整合、真实验证和交接，不能直接接受实现者自报成功。
- **使用场景：** 明确采用 Codex 作为实现者的任务
- **输入与案例：** 委派解析模块后，主 Agent 阅读完整改动并运行真实样本。
- **产出：** 实现结果与集成审查
- **调用顺序：** 明确指定 Codex 为实现者时的执行变体，不是额外必经阶段。
- **限制：** 依赖已安装、已认证的 CLI 及明确的委派范围。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/implement-spec-with-codex/SKILL.md)

### close-spec · 把计划转为长期知识

交付后归档规格，保留设计理由、约束与指向真实代码的证据。

- **具体能力：** 归档规格、清理过期计划，保留最终理由、约束、代码入口和视觉证据，核对文档与实际交付。
- **使用场景：** 功能全部完成后
- **输入与案例：** 将“下一步增加进度恢复”转为“进度如何标识、为何这样设计、测试在哪里”。
- **产出：** 归档规格与设计理由
- **调用顺序：** 所有任务与整体审查完成，汇总最终 choices.md 后归档。
- **限制：** 应逐项核对实际代码；过期计划不能直接当作最终文档。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/close-spec/SKILL.md)

### refactor-clean · 让一个概念有一个归属

检查重复抽象和临时结构，把职责收拢到清楚的边界。

- **具体能力：** 寻找重复概念或过载模块，重新划分职责，核对平台已有能力，减少多余包装；通过消费方验证行为一致。
- **使用场景：** 重构、架构审查与功能收尾
- **输入与案例：** 目录、正文和进度条各自维护阅读位置，整理为一个共同状态来源。
- **产出：** 更清晰的结构与职责边界
- **调用顺序：** review 第一步；规划与实现时也可调用，尊重真实兼容和迁移要求。
- **限制：** 已有兼容性和迁移要求必须显式保留，不能盲目删除旧路径。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/refactor-clean/SKILL.md)

### write-tests · 测试真正可观察的行为

围绕契约逐个增加测试，避免只重复实现细节。

- **具体能力：** 一次写一个行为测试，证明错误实现会失败再修复；检查实际结果，减少对内部函数、偶然样本或配置的耦合。
- **使用场景：** 行为修改、缺陷修复
- **输入与案例：** 验证刷新后恢复原段落，而不只是检查保存函数被调用一次。
- **产出：** 可复现的行为测试
- **调用顺序：** 实现和修复过程中使用，回归测试先复现失败，不必等到开发结束。
- **限制：** 需要可信的期望结果；测试通过不自动证明需求完整。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/write-tests/SKILL.md)

### audit-performance · 找到重复却不推进的工作

检查热路径、放大效应与重复执行，按真实失败风险排序。

- **具体能力：** 跟踪轮询、重试、队列和扫描，量化最坏工作量，检查每轮是否推进；核对现有上限与恢复机制，再排序修复。
- **使用场景：** 性能问题与复杂循环审查
- **输入与案例：** 每次只扫描相同的前一百项，或永久失败任务堵住队首。
- **产出：** 热点证据与有边界的修复建议
- **调用顺序：** 性能或无进展问题出现时介入；修复配合 write-tests 验证恢复能力。
- **限制：** 需要实际运行证据，不能仅凭代码外观推算性能收益。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/audit-performance/SKILL.md)

### write-docs · 留下原则与代码入口

记录长期成立的概念和理由，减少对代码清单的重复抄写。

- **具体能力：** 留下设计理由、关键概念、隐含约束和代码入口；每条事实一个主要来源，减少重复清单造成的漂移。
- **使用场景：** 共享行为变更、项目交付
- **输入与案例：** 解释翻译为何按语义分块、术语表由谁维护，并指向实现。
- **产出：** 术语、设计原则与代码指针
- **调用顺序：** review 第三步；共享行为变化和交付时更新，也可独立整理文档。
- **限制：** 文档指针和事实需要随代码核对。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/write-docs/SKILL.md)

### code-review · 从差异中找到工程问题

检查陈旧名称、死引用、无谓复杂度及低价值注释。

- **具体能力：** 检查命名、失效引用、复杂度与注释价值，沿调用关系核对，给出具体依据与结论。
- **使用场景：** 功能完成或提交前
- **输入与案例：** 函数改为多文件处理，旧名称、调用方和错误提示是否仍假设单文件？
- **产出：** 问题清单与审查结论
- **调用顺序：** review 第二步，结构稳定后审查；仅需 diff 审查时独立使用。
- **限制：** 审查意见需要回到代码验证，不能视作绝对正确。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/code-review/SKILL.md)

### audit-choices · 看见 AI 替你做的决定

追溯规格未规定的选择，记录影响、判断与信心。

- **具体能力：** 对照需求、历史与实现，追溯自主选择的数据结构、存储、依赖和接口，记录缺口、影响、判断与信心。
- **使用场景：** AI 实现后、合并前或集成委派结果时
- **输入与案例：** 本机保存进度可以运行，却无法跨设备续读，应公开这个产品取舍。
- **产出：** choices.md 决策记录
- **调用顺序：** 每轮审查后记录，合并前汇总；纯审计不改代码，修正由调用方执行。
- **限制：** 这是纯审计；发现问题后由调用方决定如何修正。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/audit-choices/SKILL.md)

### eli5 · 用具体场景解释复杂变化

从触发事件讲到结果，定义术语，让解释能够独立阅读。

- **具体能力：** 从触发事件解释到结果，定义术语，用简短伪代码讲清条件与顺序，完整说明持久数据契约的变化。
- **使用场景：** 解释规格、改动与决策
- **输入与案例：** 解释缓存失效后发生什么、哪些数据保留、用户看到什么。
- **产出：** 易理解且保持精确的说明
- **调用顺序：** 贯穿需求、方案和决策报告；是表达规范，不是固定流水线阶段。
- **限制：** 通俗表达不能省略关键条件与限制。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/eli5/SKILL.md)

### review · 把收尾检查串成一轮

依次执行结构清理、代码审查和文档检查。

- **具体能力：** 依次执行 refactor-clean → code-review → write-docs；后续修改若改变结构则返回前序步骤，最终给统一结论。
- **使用场景：** 一个实现阶段完成后
- **输入与案例：** 功能运行后继续核对状态归属、旧引用和文档入口是否一致。
- **产出：** 统一审查结论与收尾修改
- **调用顺序：** 每个实质阶段结束时使用，全部完成后审查整体；小修改按需简化。
- **限制：** 流程依赖相关技能；仍需运行项目自己的测试。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/review/SKILL.md)

### codex · 引入第二位工程审阅者

指导使用本地 Codex CLI 进行独立审查或明确授权的实现。

- **具体能力：** 指导本地 CLI 的任务范围、提示、输出和执行状态检查，并逐项核实发现与改动。
- **使用场景：** 需要第二意见或指定委派时
- **输入与案例：** 让 Codex 提供第二意见，再回到源码确认每条发现。
- **产出：** 审查报告或明确范围内的改动
- **调用顺序：** 审查或明确委派时按需使用；with-codex 变体借它执行委派。
- **限制：** CLI、认证和权限由宿主提供，指令需适配实际版本。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/codex/SKILL.md)

### claude · 使用 Claude 提供独立意见

指导通过 Claude Code 非交互调用咨询或委派任务。

- **具体能力：** 指导 Claude Code 非交互咨询或明确委派，限制范围、权限和预算，检查认证及执行问题并验证产物。

- **输入与案例：** 让另一模型检查任务拆分是否遗漏风险。
- **产出：** 咨询结果与任务交付
- **调用顺序：** 可选独立意见或实现工具；不要求与 codex 同时使用。
- **限制：** 需要本地安装、认证及合适的权限边界。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/engineering/claude/SKILL.md)

### marketing-pages · 按页面用途约束营销内容

区分活动落地页与常规页面，规定 CTA、索引和内容来源。

- **具体能力：** 区分活动页和常规可索引页面，约束 CTA、广告承诺一致性、转化衡量、站点地图和事实来源。
- **使用场景：** 营销页面创建、修改与审查
- **输入与案例：** 广告、落地页标题与注册后第一屏兑现同一承诺，价格来自统一来源。
- **产出：** 页面内容与发布规则
- **调用顺序：** 营销页面规划、实现、审查时使用；作者索引策略需按业务调整。
- **限制：** 具体索引策略是作者的工作约定，需按业务目标调整。

## 视觉审查

### compare-screenshots · 用图像证据定位差异

比较候选图与目标，生成差异图和指标，也可检查单张截图。

- **具体能力：** 先确定正确目标和可比条件，再生成并排图、灰度差异、边缘图与 JSON 指标；单图也可检查异常空白。
- **使用场景：** UI、文档、渲染与图像迭代
- **输入与案例：** 比较标题层次变化；单双色设计中留白与少颜色可能是有意选择。
- **产出：** 并排图、差异图与 JSON 指标
- **调用顺序：** 视觉验收时与 screenshot-critique 互补，分数不自动决定合格。
- **限制：** 距离分数只说明差异；低分不等于更符合设计目标。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/visual/compare-screenshots/SKILL.md)

### screenshot-critique · 给结果一双未被引导的眼睛

让新 Agent 只看截图、局部放大图与中性说明。

- **具体能力：** 新 Agent 只看完整截图、关键放大图和中性说明，指出具体可见缺陷及信心，减少实现背景引导。
- **使用场景：** 视觉验收与视觉缺陷修复
- **输入与案例：** 检查文字重叠、裁切、遮挡和阴影脱离物体。
- **产出：** 具体可见的问题及判断信心
- **调用顺序：** 视觉接受前使用，可在修复后重复；与指标比较互补。
- **限制：** 依赖独立上下文与视觉能力；第二意见仍需核对。

[固定版本原始 Skill](https://github.com/dzhng/skills/blob/3631529b7305eec8dd08b3a827f4d8c16342a29a/skills/visual/screenshot-critique/SKILL.md)

### preview-shots · 集中展示待审查图片

把精选截图放入同一个 macOS Preview 窗口。

- **具体能力：** 精选关键图片，按顺序集中打开并说明用途，避免预览窗口不断堆积。
- **使用场景：** 需要用户快速浏览视觉成果时
- **输入与案例：** 集中展示修改前、候选方案与参考图供用户判断。
- **产出：** 有顺序、有说明的图片集合
- **调用顺序：** 需要人工看图时使用；原版 macOS Preview 需做 Windows 适配。
- **限制：** 原版只支持 macOS；Windows 需要替换预览方式。

## 技能进化

### write-skills · 把经验压缩成可执行规程

定义触发条件、步骤和完成标准，按需加载参考资料。

- **具体能力：** 定义触发、步骤与完成标准；长资料按需放入 references，重复脆弱操作放入 scripts，删掉泛泛建议。
- **使用场景：** 编写或修订可复用技能
- **输入与案例：** 将开源研究的版本确认、源码阅读、证据区分和结论记录固化。
- **产出：** SKILL.md 与必要的配套文件

## 模型增强以后还有意义吗？

以下是我们的分析，不是上游效果测量或最新模型基准结论。不要把写得专业等同于确实提高任务表现。

### 可能被原生能力覆盖

命名、简单解释、通用文档建议，如果模型已经稳定做到，额外收益可能很小，应通过任务对照检验。

### 仍需外部提供的信息

项目事实、兼容要求、允许的依赖、视觉目标和验收标准，不能靠通用能力猜出，应保留这些具体约束。

### 证据与协作机制

实际测试、比较脚本、决策记录与接手说明可支持长任务。但模型审查可能共同漏项，须核对真实结果。

### 需要计算的流程成本

多 Agent、多轮规划与固定审查可能增加耗时；作者的架构与兼容偏好也未必适合现有产品。

建议用相同任务对照三组：直接交给模型、仅给精简约束与验收标准、使用完整 Skill 流程。记录成功率、漏项、返工、人工纠正次数、耗时和成本。若精简约束效果相同，就应精简完整流程。

对本仓库优先评估任务契约、决策记录和视觉证据；这些方法尚未完成对照实验，不宣称已有收益。
